## Project identity

- **Name:** Nodability
- **One-sentence description:** An AI-chat-driven personal task organizer for two named
  people (a couple), with a task board, an idea box, week/month/year calendar views, and
  light/dark theming.
- **Detailed summary:** Nodability lets a signed-in user type free-form messages into a chat
  panel ("talk to Nodo"); a cheap Claude model (Haiku) silently extracts structured tasks,
  categories, and deletions from the message, writes them to Supabase, and a capable Claude
  model (Sonnet) streams back a conversational reply grounded in the user's actual current
  task list. Tasks are also browsable/editable directly via a category-grouped board, a
  Week/Month/Year calendar, and a separate free-form "Ideas" scratchpad. Two accounts exist
  (magic-link, invite-only) and each account's data is fully isolated from the other's.
- **Target audience:** Exactly two specific real people — the developer and their partner.
  Not built for public signup or multi-tenant scale. (Verified: `shouldCreateUser: false` in
  `app/login/page.tsx`, and exactly 2 Supabase Auth users exist in production as of the audit.)
- **Main user problem solved:** Frictionless task capture — type what's on your mind in
  natural language instead of filling out a task form — plus multiple ways to review what's
  ahead (list, week, month, year).
- **Current development stage:** Actively-developed personal project in real daily use by its
  two users, not a hardened multi-tenant production SaaS. **Inferred** label:
  "post-MVP personal app" — real user data exists (19 tasks, 112 messages, 7 ideas, 3
  categories at audit time), but there are no automated tests, no CI, and `npm run lint`
  currently fails (see [Known issues](#known-issues)).
- **Production status:** Deployed and live at **https://nodability.vercel.app** (Verified:
  returns 200 on `/login`, 307→`/login` on protected routes when unauthenticated, as of the
  audit). Deploys are triggered **manually** via the Vercel CLI (`vercel --prod --yes`) —
  GitHub push does **not** auto-deploy (Verified empirically this session: a push to `main`
  did not produce a new Vercel deployment; no GitHub Actions workflow exists in this repo).
- **Repository type:** Single Next.js application, not a monorepo. Root directory `.` (Verified
  via `vercel project inspect nodability`).
- **⚠️ This repo's GitHub remote (`Gariyuuu/nodability`) is public.** This is a real
  constraint on what belongs in any file in this repo, including these documentation files:

## Architecture summary

See [ARCHITECTURE.md](ARCHITECTURE.md) for the full diagram and flow-by-flow breakdown. Short
version:

- **Rendering:** Every page **except `app/changelog/page.tsx`** is a Client Component that
  fetches its own data from the API routes via `fetch()` on mount. `app/changelog/page.tsx` is
  the one Server Component page — it renders `lib/changelog.ts`'s static array directly, no
  fetch involved. There is **no database-backed Server Component data fetching** anywhere and
  no `getServerSideProps`/RSC-database-fetch patterns in use — this is a classic
  SPA-over-API-routes shape, not an RSC-idiomatic Next.js app. (Verified via `head -1` on
  every `page.tsx`.)
- **Server/client boundary:** API routes (`app/api/*/route.ts`) and one Server Action
  (`lib/actions.ts:signOutAction`) are the only server-side code paths that touch the database.
- **Database access pattern:** All server-side DB access goes through a single **service-role**
  Supabase client (`lib/supabase.ts`), which bypasses Row Level Security entirely. Every
  query function in `lib/tasks.ts` / `lib/ideas.ts` / `lib/messages.ts` therefore takes a
  `userId` as its first argument and manually filters `.eq("user_id", userId)` — **this
  application-level filtering, not RLS, is the actual multi-tenant security boundary.**
- **Auth flow:** Magic link (Supabase OTP, PKCE) → `app/auth/callback/route.ts` exchanges the
  code for a session cookie → `proxy.ts` refreshes that cookie on every request and redirects
  unauthenticated page loads to `/login` → API routes independently call
  `lib/auth.ts:requireUserId()` and return 401 JSON if there's no session (this is intentional
  defense-in-depth, not redundancy to remove).
- **AI flow:** User message → `app/api/chat/route.ts` → `lib/categorize.ts` (Haiku, forced
  tool-use, extracts tasks/deletions) → writes to DB via `lib/tasks.ts` → builds a grounding
  context block from current open tasks + an "actions just taken" log → streams a Sonnet reply
  back to the client → persists both messages via `lib/messages.ts`.
- **State management:** Local `useState`/`useEffect` per component. No global state library,
  no React Context beyond `ThemeProvider`.
- **Caching:** None beyond Next.js's default static generation of purely-static routes
  (`/icon`, `/apple-icon`, `/changelog`, etc. — see the build output's route table).
- **Background/scheduled jobs:** None exist in this repo.

## Coding conventions

**Verified** (observed consistently across the codebase, not aspirational):

- Server-only DB query functions live in `lib/*.ts`, always take `userId: string` as the
  first parameter, and throw on Supabase error (`if (error) throw error;`) rather than
  swallowing it.
- API routes follow a consistent try/catch pattern: call `requireUserId()`, catch
  `UnauthorizedError` → `NextResponse.json({ error: "unauthorized" }, { status: 401 })`, else
  rethrow. **Exception:** `app/api/chat/route.ts` only wraps the `requireUserId()` call this
  way; the rest of its body has no error handling (see [Known issues](#known-issues)).
- Components are function components with named default exports, `"use client"` at the top
  of every interactive file.
- Styling is Tailwind utility classes using this app's **semantic color tokens** (`bg-bg`,
  `text-fg`, `bg-surface`, `border-border`, `text-muted`, `bg-accent`, `text-accent-fg`) —
  never raw Tailwind palette classes like `bg-gray-100` (those were deliberately removed
  during the theming pass; reintroducing them would break dark-mode/palette support — see
  [UI_SYSTEM.md](UI_SYSTEM.md)).
- Path alias `@/*` maps to the repo root (`tsconfig.json`), e.g. `@/lib/tasks`, `@/components/Sidebar`.
- No barrel files (`index.ts` re-exports) anywhere — every import is a direct file path.
- Dates are ISO-8601 strings (`YYYY-MM-DD`) end-to-end; times are 24-hour `HH:MM`. Formatting
  to human-readable strings happens only at render time in `lib/format.ts`.
- SQL migrations are numbered (`002_`, `003_`, ...), forward-only, with a comment at the top
  explaining what they do and how to run them. **001 does not exist** — `supabase/schema.sql`
  is the implicit "migration 001" (Inferred from numbering gap).

**Newly recommended** (not yet established, but would fit the existing style): if a test
framework is added, colocate `*.test.ts` next to the file under test rather than a separate
`__tests__` tree, to match this repo's otherwise-flat, colocated style.

## UI and design system

Full detail in [UI_SYSTEM.md](UI_SYSTEM.md). Key facts every session should know up front:

- **Theme tokens are defined in `app/globals.css`**, as CSS custom properties scoped by
  `[data-palette]` and `[data-theme]` attributes on `<html>`, then re-exposed as Tailwind v4
  utilities via an `@theme inline` block (`--color-bg`, `--color-fg`, etc. → `bg-bg`,
  `text-fg`, ...). There is **no `tailwind.config.js`** — Tailwind v4's CSS-first config is
  used exclusively.
- **4 palettes:** Slate, Ocean, Sunset, Forest — each with a light and dark variant (8 total
  variable blocks in `globals.css`). Palette + mode are chosen via `components/theme/ThemeToggle.tsx`
  and persisted to `localStorage` (`lib/theme.ts` constants `THEME_STORAGE_KEY` /
  `PALETTE_STORAGE_KEY`).
- **Backgrounds are real hotlinked photos** from `images.unsplash.com` (one specific photo ID
  per palette, same photo for light/dark, darkened/lightened via a CSS scrim gradient layered
  on top). These are **external URLs, not local assets** — see
  [DO NOT CHANGE WITHOUT REVIEW](#do-not-change-without-review).
- **No-flash-of-wrong-theme script:** an inline `<script>` in `app/layout.tsx`'s `<head>`
  (string built in `lib/theme.ts` as `NO_FLASH_SCRIPT`) reads `localStorage` and sets
  `data-theme`/`data-palette` on `<html>` before first paint. Removing this reintroduces a
  flash-of-default-theme on every load.
- **No component library** (no shadcn/ui, no Radix, no MUI) — every UI element is hand-rolled
  with Tailwind classes.
- **Icons:** `app/icon.tsx` / `app/apple-icon.tsx` use `next/og`'s `ImageResponse` to render a
  gradient "n" mark at request time (statically cached by Next.js). No icon font or SVG icon
  library is used elsewhere; inline emoji are used for small decorative marks (🌱 for the chat
  avatar, 🎨 for the theme toggle button).
- **Responsive design:** Minimal — the main board (`app/page.tsx`) uses a fixed 3-column
  desktop layout (`Sidebar` / `TaskBoard` / `ChatPanel`, `w-96` chat panel) with **no mobile
  breakpoint handling**. The week/ideas/templates/changelog pages use `max-w-*` centered
  containers that do reflow reasonably on narrow screens, but nothing was verified on an
  actual mobile viewport. **Inferred gap, not a confirmed bug.**
- **Accessibility:** Basic `aria-label`/`title` attributes exist on icon-only buttons (delete
  buttons, theme toggle, group dots). No systematic a11y audit has been done.

## Database summary

Full detail, including a Mermaid ER diagram, in [DATABASE.md](DATABASE.md). Short version:

- **Provider:** Supabase (managed Postgres), project ref `hwvqnenmnrzdncwznorv`.
- **Schema source of truth:** `supabase/schema.sql` + `supabase/migrations/002..005*.sql`,
  applied **in order, manually**, via the Supabase SQL Editor. There is no automated
  migration runner.
- **Tables:** `categories`, `tasks`, `messages`, `ideas` — all 4 have `user_id uuid not null
  references auth.users(id)`, RLS enabled, and an owner-only RLS policy
  (`user_id = auth.uid()`). RLS is **defense-in-depth only** — the app's actual server code
  always uses the service-role client, which ignores RLS.
- **Live data at audit time:** 19 rows in `tasks`, 112 in `messages`, 7 in `ideas`, 3 in
  `categories`. **This is real data belonging to real people — treat destructive operations
  accordingly.**
- **Known schema risk:** `categories` has a `unique(user_id, name)` index (case-sensitive),
  but application code looks up categories case-insensitively (`.ilike()`). A race or a
  manually-inserted row could create two categories differing only by case
  (e.g. "Chemistry" and "chemistry") that the app would then treat inconsistently.

## Authentication and authorization

Full detail in [SECURITY.md](SECURITY.md) and [API_REFERENCE.md](API_REFERENCE.md). Short
version:

- **Signup:** None — no public signup UI or flow exists anywhere in the codebase.
- **Login:** Magic link only (`app/login/page.tsx` → `supabase.auth.signInWithOtp({
  shouldCreateUser: false })`). Because `shouldCreateUser` is `false`, only pre-existing
  Supabase Auth users can request a link — this is the entire access-control mechanism for
  "who is allowed to use this app."
- **Account provisioning:** New accounts are created **out-of-band** by running
  `scripts/create-users.mjs <email>` locally with the service-role key. There is no in-app
  invite flow.
- **Logout:** `lib/actions.ts:signOutAction` (Server Action), wired to a form in
  `app/page.tsx`'s header.
- **Session handling:** `@supabase/ssr` cookie-based sessions; refreshed on every request by
  `proxy.ts`.
- **Roles/permissions:** None — there are exactly two account types, both identical
  ("owner of their own data"). No admin role, no shared/team data model.
- **Protected routes:** Every route except `/login` and `/auth/callback` (see
  `PUBLIC_PATHS` / the proxy `matcher` config in `proxy.ts`, which also excludes `/icon` and
  `/apple-icon` so the favicon loads for logged-out visitors).
- **Ownership checks:** Enforced in application code (`userId` filtering in `lib/tasks.ts` /
  `lib/ideas.ts` / `lib/messages.ts`), backed by RLS as a second layer.

## API and integrations

## Known issues

### ISSUE-001 — ESLint fails with 9 errors
- **Severity:** Low (does not block build or deploy; purely a lint-only signal)
- **Status:** Open, unaddressed
- **Affected files:** `app/ideas/page.tsx:27`, `app/week/page.tsx:32`,
  `components/TaskBoard.tsx:35`, `components/theme/ThemeProvider.tsx:40` (all
  `react-hooks/set-state-in-effect`); `components/ChatPanel.tsx:79`
  (`react/no-unescaped-entities`, an apostrophe in "you've"); `lib/tasks.ts:105,235,236,251`
  (`@typescript-eslint/no-explicit-any`).
- **Reproduction:** `npm run lint` — exit code 1.
- **Suspected cause:** The `set-state-in-effect` errors are all the standard "fetch on mount"
  pattern (`useEffect(() => { load(); }, [deps])` where `load` calls `setState`) — a newer,
  stricter rule in `eslint-config-next` 16 flags this even though it is a common, functionally
  correct pattern. The `no-explicit-any` errors are from typing raw Supabase join-row shapes.
- **Attempted fixes:** None yet.
- **Recommended next investigation:** For the effect errors, either wrap the fetch in a
  named async function called from an event handler pattern the rule accepts, or scope-check
  whether disabling this specific rule project-wide is more appropriate than restructuring 4
  components. For the `any` errors, define a proper Supabase join-result type instead of
  `any`. See `TASKS.md` task `BUG-001`.
- **Workaround:** None needed — lint is not gating anything currently.

### ISSUE-002 — `/api/chat` has no error handling past the auth check
- **Severity:** Medium (real user-facing failure mode, not yet observed/reported by the user
  but logically certain from the code)
- **Status:** Open, unaddressed
- **Affected files:** `app/api/chat/route.ts` (lines 26–141)
- **Reproduction (inferred, not manually triggered):** Any thrown error after the
  `requireUserId()` check — e.g. Haiku failing to return the forced `extract_tasks` tool call
  (`lib/categorize.ts:129`, `throw new Error(...)`), a malformed request body, or any Supabase
  write failure — becomes an unhandled promise rejection. Next.js converts this to a bare 500
  response. `components/ChatPanel.tsx`'s `fetch()` does not check `res.ok` before reading the
  response body as a stream, so the error page's raw text would be rendered into the chat
  bubble as if it were the assistant's reply, instead of showing the intended "Something went
  wrong reaching the assistant" message (that catch block only fires on a *network*-level
  fetch failure, not an HTTP error status).
- **Suspected cause:** Inconsistency with the try/catch pattern used in every other API route
  (`app/api/tasks/route.ts`, `app/api/ideas/route.ts`, `app/api/categories/route.ts`,
  `app/api/templates/route.ts`) — the chat route was written first and never retrofitted with
  the same defensiveness.
- **Recommended fix:** Wrap the route body in try/catch, return a proper JSON/text error
  response with a non-200 status, and update `ChatPanel.tsx` to check `res.ok` before reading
  the stream. See `TASKS.md` task `BUG-002`.
- **Workaround:** None — has not caused a reported incident yet, but is unverified/unmitigated.

### ISSUE-003 — Life-area grouping feature is built but unused in production data
- **Severity:** Low (not a bug, a discoverability/UX gap)
- **Status:** Open
- **Affected files:** `components/Sidebar.tsx` (the colored dot), `lib/groups.ts`
- **Detail:** All 3 live categories currently have `group_name = 'other'` (Verified via direct
  DB query at audit time) — meaning the two real users have never used the group-cycling dot,
  likely because it's a small unlabeled colored dot with only a hover tooltip. The
  calendar's group filter therefore currently shows everything under "Other" in practice.
- **Recommended next step:** Either make the control more discoverable (a label, not just a
  dot) or reconsider whether manual tagging is the right UX for this feature.

### ISSUE-004 — Unsplash-hotlinked theme backgrounds are an unmanaged external dependency
- **Severity:** Low
- **Status:** Open, accepted risk (documented, not yet mitigated)
- **Affected files:** `app/globals.css` (`--bg-art` values reference
  `https://images.unsplash.com/photo-<id>` URLs directly)
- **Detail:** If Unsplash ever removes/rotates these specific photo IDs, the background
  silently degrades to just the flat scrim color (no broken-image icon, since it's a CSS
  `background-image`, but the "real photo" effect disappears without any error or fallback).
  No local copy of these images exists in `public/`.
- **Recommended fix:** Consider self-hosting the 4 chosen images in `public/` instead of
  hotlinking, for durability.

### ISSUE-005 — Templates can be applied more than once, duplicating tasks
- **Severity:** Low
- **Status:** Open
- **Affected files:** `app/api/templates/route.ts`, `lib/templates.ts`
- **Detail:** `getOrCreateCategory` is idempotent (won't duplicate categories), but
  `insertTask` always inserts — clicking "Use this template" twice on `/templates` creates two
  copies of that template's example tasks.
- **Recommended fix:** Either disable the button after first use per session, or check for an
  existing task with the same title/category before inserting.

## DO NOT CHANGE WITHOUT REVIEW

- **`supabase/migrations/*.sql` — never edit a migration that has already been run in
  production.** Add a new numbered migration instead. `004_user_scoping.sql` in particular
  must run in its documented two-pass order (see the comment at the top of that file) —
  running it as one paste will fail because Pass 2's `NOT NULL` constraint requires the
  manual backfill step in between.
- **`lib/supabase.ts`** — the service-role client. Never import it from a `"use client"`
  component (it would leak the service-role key to the browser bundle). It is intentionally
  the *only* client used by `lib/tasks.ts`/`lib/ideas.ts`/`lib/messages.ts` — do not swap it
  for the session-aware client there, since every one of those functions relies on being
  passed `userId` explicitly and filtering manually; RLS is not a substitute unless every call
  site is also re-audited.
- **`proxy.ts`** — the auth gate. Changing its `matcher` config or `PUBLIC_PATHS` list can
  either lock out all users (if a needed public path is removed) or expose protected data (if
  a path is wrongly added to the public list). `/icon` and `/apple-icon` must stay excluded or
  the favicon breaks for logged-out visitors (this was an actual bug introduced and fixed
  during this session).
- **`app/api/*/route.ts` auth pattern** — every route must call `requireUserId()` and scope
  every DB call by the returned `userId`. Skipping this on a new route would leak one user's
  data to the other.
- **`.env.local`, and the Vercel dashboard env vars** — never commit real values. Rotating
  `SUPABASE_SERVICE_ROLE_KEY` requires updating both `.env.local` and the Vercel dashboard
  (Production **and** Preview scopes).
- **`categories.name` uniqueness (`unique(user_id, name)`)** combined with the app's
  case-insensitive `.ilike()` lookups — do not "fix" this by relying on the DB constraint
  alone; either keep the case-insensitive check-before-insert pattern in `getOrCreateCategory`
  or add a case-normalizing constraint, but don't remove one without the other.
- **Theme CSS variable names** (`--bg`, `--fg`, `--surface`, `--border`, `--muted`, `--accent`,
  `--accent-fg`, `--bg-art`) in `app/globals.css` — these are consumed by the Tailwind
  `@theme inline` block and referenced by name throughout every component's className strings.
  Renaming one requires updating every usage across `app/`, `components/`.
- **`scripts/create-users.mjs`** — uses the service-role admin API to create real
  authentication accounts. Never run it against production without knowing exactly which
  emails you're adding; there is no corresponding "delete user" script (deletion was done
  manually via an ad hoc script this session, not committed to the repo).
- **Live production data** — 19 tasks / 112 messages / 7 ideas / 3 categories belonging to
  2 real people, at the time of this audit. Never run destructive SQL, a DB reset, or a bulk
  delete against the production Supabase project without explicit user confirmation.
